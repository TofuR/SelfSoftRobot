# 10 Hz 下反馈超时与“0 / 0 ms”排查

2026-09-11。当前执行日志中斜线两侧原本表示 **控制线程等待反馈的时间 / 开始反馈前剩余的计算预算**，不是算法耗时 / 100 ms。旧界面将不存在的字段默认写成 0：例如没有新图像时根本没有开始计算，却可能显示 0 / 0。新界面缺失值显示 `—`，区分“本步未计算”“预算耗尽”“上次仍在计算”“本次未按时提交”。真实测得的零仍显示 0。

## 本次找到并修复的等待问题

真实阀的路径原为 `串口线程 → ModbusManager → ValveController → QtValveTransport`，其中 ACK 转发依赖 GUI 事件循环。即使串口已经收到正确应答，GUI 绘图/日志处理忙时，执行线程仍可能没有收到通知。

通过模拟串口驱动实际上述信号链，暂停 GUI 事件处理，复现“两个正确 ACK 已收到、控制线程仍等待超过 200 ms”。修复后 ACK 与错误通知直接进入带锁的命令记录并唤醒控制线程；GUI 显示仍由 GUI 线程处理。阀命令下发依然在控制器所属 Qt 线程中，压力映射、上下限、变化率、应答检查和超时丢弃规则保持。

这证明存在软件等待问题，不证明今天现场的全部超时都由它引起；没有获取用户设备电脑上的实际记录。本次未连接物理串口或 D415。

## 如何看新日志

| 字段/显示 | 含义 | 偏大时检查 |
|---|---|---|
| `dispatch_wait_ms` | 控制线程请求到控制器实际发起命令的等待 | GUI 发令调度、界面阻塞 |
| `ack_ms` / ACK | 发起命令到两组应答验证完成中较晚者 | 串口队列、传输、设备响应、驱动/线程；不等于纯线路传输 |
| `ack_delivery_ms` / ACK 后唤醒 | 最后 ACK 的时间戳到 `send()` 返回 | 应答通知、线程唤醒、调度；不是额外的物理阀响应 |
| `send_wait_ms` | 本次阻塞 `send()` 的总时间 | 结合上述三项区分发令等待、通信与通知等待 |
| `frame_wait_ms` / 等图 | `send()` 返回后等待满足时间条件的新图像 | 相机实际帧率、新帧时间戳、额外等图参数 |
| `camera_poll_count` | 本周期查找新图像的次数 | 0 表示没有进入等图循环，常见于通信返回时期限已过 |
| `frame_age_at_selection_ms` | 取用时距相机接收时间戳的间隔 | 缓存/处理延迟；不是曝光年龄 |
| `frame_after_ack_ms` | 选中图像接收时间减 ACK 时间 | 等到了哪一帧；不是 USB 传输耗时 |
| `feedback_budget_ms` / 可用预算 | 开始反馈前距本周期期限的剩余时间 | 预算为 0 时，算法可能根本没有开始 |
| `feedback_wait_ms` / 等待反馈 | 执行线程实际等候本次工作任务的时间 | 不等于超时候选的完整计算时间 |
| `compute_ms` / 计算 | 已取得结果的反馈实际计算时间 | 边缘搜索、状态修正、动作优化；未完成则不填 0 |

这些字段保存在每次执行的 `timings.csv` 和 `steps.jsonl`。候选完成后的实际时间另见 `feedback_jobs/*.json`，包括已被截止时间规则丢弃的任务。以第一页保存根目录为准，路径为 `<保存根目录>/hereditary/<会话>/executions/<执行编号>/`。

例如 ACK 25 ms、ACK 后唤醒 80 ms，此时 100 ms 周期已耗尽，即使算法只需 30 ms，也来不及启动。这种情况不应该解释成“30 ms 算法用了超过 100 ms”。另一方面，ACK 30 ms＋等图 30 ms＋其他开销 5 ms 后，扣除 3 ms 预留，仅约 32 ms 预算；算法偶发 45 ms 也会被丢弃。

## 阀与相机已经核对的行为

- 两组阀使用各自串口线程并行收发，不是先等组 1 再发组 2。默认 9600 baud、8N1，一组 15 字节请求＋8 字节应答在线路上约 24 ms，另有设备处理、USB/驱动与排队时间。0.1 s 串口读取超时是没收齐字节时的上限，不代表每次必等 100 ms。不擅自改波特率；设备端也必须支持并配套配置。
- 相机默认请求 640×480、30 FPS，控制模型 10 Hz 与相机帧率独立。控制器读取的是采集线程直接写入的独立缓存，已经不依赖 GUI 显示队列。SDK 的 `wait_for_frames(1000)` 是最长等候上限，新帧到达就返回，不是每帧固定等 1 s。
- 保留“ACK 后接收的新图像”的时序规则，没有改成使用旧帧。取消了查找图像前无条件等待 5 ms；先检查已有满足条件的新帧，确实没有时再短时等待。
- 第四页“发令后额外等图”通常保持 0 ms；增加它会减少反馈预算。相机时间戳是主机接收时间，当前记录不能单独分离曝光时间与 USB 传输时间。

建议先使用本次通信修复，依据上述字段定位现场瓶颈。性能分析中的局部图像与减少动作块仍是离线候选，本次没有替换默认矫正算法。

后续新增了 [分频控制](MULTIRATE_CONTROL.md)：第四页间隔大于 1 时，后台计算可跨动作周期，主动间隔步不算超时；`feedback_application` 区分旧任务在本步的采用结果。它可以减少计算对发令的阻塞，但不能消除阀通信自身超过控制周期的情况。
